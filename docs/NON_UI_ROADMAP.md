# 时政项目非界面功能待办规划

更新日期：2026 年 11 月 12 日。

目标是为考研、考公用户自动整理最新时政：稳定采集权威媒体和精选自媒体，把同一事件的多篇报道关联起来，按集中报道程度与备考相关性区分重要性，再生成带原文依据的摘要和备考解读。

实施主线：采集质量与持续入库 → 事件聚合 → 报道统计与评分 → 有来源的 AI 总结 → 每日与周期资料 → 多用户试用与上线。

## 下一阶段工程规划（2026-11-13）

本节作为接下来的执行顺序，优先于本文后续保留的早期建议。这里只规划后续工作，不表示已实施，也不自动启动部署、付费模型或外部推送。

### 产品目标与范围

首版暂按“自己与朋友使用、重点服务考研政治”规划；公考与申论保留已有入口，暂不同时扩大新功能。目标是让用户完成：看到今天值得学的内容 → 理解和核对 → 回想作答 → 收藏或加入复习 → 下次继续。

公众号提供讲解与背诵线索，权威来源用于事实和原文核对。按考点组织两类内容，保留来源区别；不会把作者观点、作者标星或押题判断自动升级为系统结论。具体考试年份、教材版本和开放范围仍需确认。

- [ ] 正文变更创建版本；引用绑定文章版本与段落，不让更正后的新段落编号覆盖旧依据。

验收：用同一篇两个修订版本验证更新和历史回溯；以“同一次发布多篇、停机后连续发布数篇”为采集覆盖用例。无法补齐时状态必须为部分覆盖。不要靠提高请求频率假装解决覆盖问题。

### 第二批：从“按文章看”转为“按考点学”

建议增量模型，不推倒已有新闻与学习资料：

- SourceArticle / ArticleVersion：来源文章及不可变修订版本；现有 News 与 LearningMaterial 保留兼容映射。
- KnowledgePoint：稳定编号、学科章节、考试年份/教材版本、名称及别名。
- Evidence：文章版本、段落 ID、原文片段、支撑哪一条结论及适用范围。
- StudyCard：问题、答案、知识点、证据与审核状态；作者重点标记与系统排序理由分字段。
- ReviewRecord：用户对一张卡的回想结果与下次复习时间，先使用浏览器本地记录，后续需要跨设备再扩展。

实施要求：

- [ ] 先选 10–20 个实际考点建立人工关系样本，作为规则与后续语义模型的共同评测集。
- [ ] 先用规范化术语、章节及人工确认建立关系；不只按关键词、相同标题或作者标星自动合并。
- [ ] 同一考点下列出两位老师的对应材料与差异；冲突留待确认，不拼成一个无来源答案。
- [ ] 权威新闻仅在能支持某考点的事实或政策原文时关联；无关新闻留在资料库。
- [ ] 统一检索返回新闻、学习资料和考点，并明确内容类型；筛选条件、分页与来源链接保留。
- [ ] 老的 `/news/{id}`、`/learning/{id}` 和本地收藏键继续有效；可增加跳转到考点入口。

验收：选一个确实有多来源支持的考点，展示“考点 → 对照材料 → 证据 → 自测”的闭环；不要为演示而把 D28 思法与 D26 经济内容强行关联。人工标注样本上的误关联与漏关联分别记录。

### 第三批：学习入口整合，而非再增加一个独立栏目

- [ ] 在现有首页内逐步加入“今天的新材料、可复习考点、待复习卡片”，控制首屏信息量。
- [ ] 每日清单按新增材料、人工确认重点与用户未学内容组织，给出入选理由；不承诺押题概率。
- [ ] 无新文章时显示真实状态与可复习内容，不伪造每日更新。
- [ ] 收藏入口继续全站共用；支持从已收藏资料进入对应考点或加入复习，不将收藏直接视为已掌握。
- [ ] 先完成一个考点和一组问答的完整路径，再决定是否需要调整四个主导航的职责，避免反复重做 UI。

验收：用户无需理解“抓取、导入、抽取”这些内部阶段，就能找到今天值得学的内容；三次以内的主要操作能进入对应考点自测。该操作数量是设计目标，需用实际试用验证。

### 模型接入与质量门槛

- 只向模型提供所选考点的相关证据，按文章指纹、提示词版本、模型配置和输出版本缓存；不每次刷新网页重新总结。
- 输出结构包括核心事实/考点、背诵提纲、易混点、来源差异、未确定事项及逐条引用；回答不得超出已提供材料。
- 关键数字、日期、否定词、范围词和引用 ID 做程序检查，检查失败进入待审核；检查通过也不等于内容完全正确。
- 只有可信证据足够时才生成统一结论；模型不可用、超时或预算耗尽时保留原文、规则卡片和已审核版本。
- 基于人工样本比较是否更省时、是否遗漏重点、是否曲解原意；先确定质量基线，再选择具体模型，不用“接上 API”代替验收。

### 暂缓事项与需要确认的信息

暂缓：扩展更多公众号、全平台爬虫、大规模历史回填、完整题库、复杂账号体系、跨设备同步、分布式架构和大面积视觉重做。

需要逐步确认，但不阻塞 E01–E03：

1. 首版对应哪一届考试、哪一版教材，是否仅聚焦考研政治。
2. 哪个模型服务可用，每日费用上限和允许发送的材料范围；密钥只放本地配置。
3. 仅自己/朋友私用，还是准备公开；文章与衍生材料的可展示范围。
4. 谁来确认有歧义的考点，是否先以“待核对材料”形式开放。

- [x] 区分应用启动、近期同步、历史回填开关；增加可关闭调度器的配置。
- [x] 检查同步周期实现：当前使用 cron 小时步长，不能把所有取值都理解成严格的每隔若干小时。

验收：按文档可在干净 Python 3.13 环境安装；Windows 正确识别北京时间；关闭采集后启动和查询均不产生采集请求。

## 工作包 2 采集可靠性和持续入库

涉及现有 `app/fetch_news.py`、`app/sync_service.py`、`app/tasks.py`。

### T03 建立来源清单和逐源体检

- [ ] 为每个来源记录名称、媒体或账号类型、允许域名、频道、采集方式、抓取频率、启停状态及解析器版本。
- [ ] 实测已有 JSON、RSS、HTML 地址，分别统计列表请求成功数、候选数、详情成功数、日期有效数和最终入库数。
- [ ] 更新失效归档地址。当前“遇到 404 跳过”的修复只能减少浪费，不能证明来源已修复。
- [ ] 区分健康、部分失败、空列表、解析失败、有效新闻为空等状态。
- [ ] 对 RSS 与 HTML 按来源及通道分别记录，再汇总来源健康；避免后一个通道覆盖前一个通道的结果。

验收：一次受控同步后，能说明每个来源新增几条、过滤几条及原因；失败来源不阻断其他来源。

### T04 修正日期和正文提取

- [ ] 优先读取文章元数据和媒体专用的发布时间节点；不要把全网页第一处日期当作文章日期。
- [ ] 分别保存发布时间、首次发现时间、抓取时间和事件发生时间；未知时间保持未知，不能自动伪造为今天。
- [ ] 标记日期精度及推断来源，只有日期时不能参与精确到小时的传播速度比较。
- [ ] 校验详情解析后的日期仍在目标时间范围内。当前部分路径在补详情前筛选，补详情后可能改写日期。
- [ ] 正文提取排除导航、版权、相关推荐等噪声，处理字符编码、网页正文和长政策材料。
- [ ] 区分列表导读、正文节选、可用于分析的正文与生成摘要，避免混用同一个字段。
- [ ] 正文失败记录明确状态，不把标题当成完整正文通过质量检查。
- [ ] 对允许获取和处理的长文保留足够分析材料，前台仍可以仅展示节选；不能让当前约 1200 字节选成为政策总结的全部证据。

验收：用各媒体固定网页样本测试；页面含多个历史日期时仍能正确提取文章日期；缺正文的文章不会触发正常 AI 总结。

### T05 增量采集和逐批提交

- [ ] 从“全部来源和详情抓完后统一入库”改成按小批次持续入库，保存成功一批即可查询。
- [ ] 按来源保存同步游标和最近成功时间，允许小范围重叠扫描以发现延迟稿件及更正。
- [ ] 优先处理近期新内容，删除截断前随机打乱的策略，使用确定性的来源配额和时间顺序。
- [ ] 在抓取详情前就去重和设置预算；当前结果上限 40 条不代表最多请求 40 篇详情。
- [ ] 分开限制列表页数、详情请求数、最终入库数和总任务时长。
- [ ] 已存在文章按内容指纹判断是否需要更新，减少重复请求和无效索引写入。
- [ ] 网络请求增加每域名限速与有限并发，保留临时失败重试及限流处理。

验收：慢来源存在时，快来源成功的数据仍能提前入库；重复同步不会增加重复记录；新增、更正和失败重试结果可预测。

### T06 修复历史回填的月份边界

- [x] 统一按月份编号计算起止范围，移除一月份按年份倒退的特殊分支。
- [x] 覆盖一月、十二月、闰年、批次不足以及跨年场景。
- [ ] 避免重复补齐已经完整成功的批次；不要把“最早和最新日期存在”当作所有历史资料完整。

具体风险：现有 `month_batches` 在一月份处理两个月一批时，会把起点退到上一年一月，而预期应为上一年十二月，可能抓取远超配置的范围。

验收：每批覆盖的日历月份数与批次计数一致，批次之间没有遗漏或意外重叠。

### T07 持久化任务进度和恢复

- [ ] 建立同步任务、来源子任务和失败条目记录，明确排队、运行、成功、部分成功、失败和取消状态。
- [ ] 实时保存当前来源、阶段、候选数、详情成功数、入库数、跳过原因和最近进度时间。
- [ ] 支持取消、超时退出、失败重试及重启后识别中断任务。
- [ ] 修复状态清理失败导致锁不释放的风险，用可靠的最终释放逻辑收尾。
- [ ] 小规模先使用单一采集执行者；多进程前引入共享任务锁或独立 worker，不能仅依赖 `threading.Lock`。
- [ ] 耗时采集、聚合和模型调用放在后台；接口只创建任务并返回编号，避免 `async def` 路由直接执行阻塞工作。

验收：重启后不会永远显示“同步中”；重复点击不会产生重复任务；单来源失败有可追踪记录。

## 工作包 3 数据模型和后端职责

### T08 建立数据库迁移

- [ ] 引入版本化数据库迁移流程，新字段和新表可升级、备份和回滚；不要只依赖 `create_all`。
- [ ] 保留已有新闻及原文链接，新增字段提供可控回填与默认值。
- [ ] 首版继续使用 SQLite。正式决定支持 PostgreSQL 时，分别实现建表、搜索和事务适配。

当前生产 Compose 使用 PostgreSQL，而启动时无条件创建 SQLite 专用 FTS5 表，不能直接把数据库地址换成 PostgreSQL 就上线。

验收：真实库副本可从现有结构升级，新功能不丢旧数据；未支持的数据库配置明确报错。

### T09 拆出可独立测试的服务

- [ ] 来源适配器负责获取和解析；文章服务负责清洗、去重和保存。
- [ ] 事件服务负责关联报道；评分服务负责可解释排序；摘要服务负责模型与验证。
- [ ] 调度和任务服务负责编排，不把全部业务继续堆进 `fetch_news.py`。
- [ ] 查询接口返回稳定的数据结构，避免评分和分组只存在于 HTML 拼接过程中。
- [ ] 与 UI 对话协调 API 字段；修改页面依赖前先约定接口，不覆盖对方文件。

建议新增的职责目录为 `sources`、`services`、`repositories`，具体命名可按现有结构调整。保持单体应用即可，首版不需要拆微服务。

## 工作包 4 事件聚合和稿源追踪

### T10 设计事件及关联数据

- [ ] 新闻文章仍保留独立记录；新增事件、事件文章关系和事件版本。
- [ ] 事件保存标题、标签、首次发现、最近进展、涉及实体、状态及代表文章。
- [ ] 关联记录保留归类方法、置信度和人工修订结果。
- [ ] 事件拥有稳定编号，标题修改或代表文章变化后收藏、摘要与接口引用仍有效。
- [ ] 区分刊载媒体与原始稿源；同一机构多个频道不重复计算为多家媒体。
- [ ] 保留合并与拆分记录，使误合并可以恢复。

### T11 从链接去重升级到同事件识别

- [ ] 规范化 URL，清除可确认无语义的跟踪参数；计算正文指纹。
- [ ] 第一层识别同链接、同正文、转载与近似标题。
- [ ] 第二层使用标题、正文、人物、机构、地点和时间范围寻找候选事件。
- [ ] 需要时增加语义向量或模型辅助判定；阈值通过标注样本调整，不能仅凭主观常数决定。
- [ ] 区分“政策发布”“政策解读”“后续落实”和“不同年份相似事件”；同一主题不等于同一事件。
- [ ] 不确定时暂不合并，优先避免把不相干的事实放进同一总结。

验收：准备至少 100 对有人工标签的文章关系样本，包含不同标题同事件、同标题不同日期、转载和后续进展；分别记录误合并与漏合并。首轮以误合并尽量低为目标，阈值和质量目标在试用前确定。

### T13 将热度和学习价值分开评分

- [ ] 热度使用时间窗口媒体覆盖、增长速度和时效衰减。

- [ ] 保存评分版本、各项得分与入选理由，提供人工置顶、降级和撤回能力。
- [ ] 用人工整理的一段时间样本校准排序，权重是可调整的产品参数，不是考试概率。

## 工作包 6 大模型总结和备考解读

### T14 接入可替换的模型服务

- [ ] 确定服务商、模型、API 地址、是否允许材料发送至该服务及日预算。
- [ ] 建立统一模型调用接口，覆盖超时、限流、重试、失败状态和关闭开关。
- [ ] API Key 仅在后端配置，示例配置使用占位符，不进入前端、Git 或日志。
- [ ] 先使用 API；没有明确离线需求时不自行训练或部署大模型。
- [ ] 采集与模型任务分开，模型不可用仍可采集、检索并阅读原文。

### T15 规定结构化内容和证据

- [ ] 一句话事件概括、若干核心事实、关键日期与数字、来源文章及证据片段。
- [ ] 事实摘要与考研政治、公考常识、申论面试解读分别存放，明确解读的生成属性。
- [ ] 重要表述保留原文措辞与上下文；不把摘要中的改写当作官方原话。
- [ ] 教材、考试大纲、真题关联使用可核对的材料及版本；未提供依据时只输出阅读角度，不编造“历年考点”。
- [ ] 多源冲突保留差异，待核实信息不写成确定事实。
- [ ] 政策长文按章节整理，再综合全文；缺关键章节时明确限制输出。
- [ ] 来源网页仅作为材料处理，不允许网页里的文字改变系统指令、索要密钥或调用工具。

### T16 校验和审核生成结果

- [ ] 校验 JSON 结构、必要字段、引用文章编号和证据是否真的存在。
- [ ] 核对关键数字、单位、日期、机构名、政策名称与适用条件，发现冲突进入待审核状态。
- [ ] 对无正文、材料不足或引用失败的事件停止自动发布总结。
- [ ] 提供审核、修订、驳回、重生成和撤回接口，保留修改记录。
- [ ] 首轮用 30 至 50 个事件人工审核，覆盖政策文件、国际动态、科技和民生。该数量是建议的试用样本，不是已完成工作。

验收：每条核心事实可追溯到具体材料；模型失败不会变成“生成成功”；首版公开自动总结前完成一轮人工审核。

### T17 控制费用和版本

- [ ] 保存模型标识、提示词版本、输入文章版本、生成时间、校验结果、审核状态及用量。
- [ ] 用输入内容指纹缓存结果，重复同步不重复付费生成。
- [ ] 事件有实质进展才更新，新增相同转载不触发重复总结。
- [ ] 设置单任务、单日预算和有限并发，超限排队或暂停。
- [ ] 估算按模型真实计价和试用输入长度计算，不预先承诺固定月费用。

验收：能查出一份总结依据哪批报道、由哪个配置生成及消耗多少；模型重试不会无限累计费用。

## 接口和数据契约

以下是建议新增的资源，不是当前已经存在的接口。与 UI 对话确认后再定路径。

| 资源 | 建议包含的数据 | 用途 |
| --- | --- | --- |
| 来源 | 类型、账号、解析版本、通道状态、最近成功时间 | 管理采集和解释数据来源 |
| 新闻文章 | 原文、正文状态、日期精度、稿源、内容指纹 | 保存证据与去重 |
| 事件 | 稳定编号、标题、主题、时间、关联报道、进展 | 以事件组织阅读 |
| 评分 | 统计窗口、媒体数、独立稿源数、分项理由、规则版本 | 解释推荐顺序 |
| 总结 | 事实、分方向解读、引用、输入版本、审核状态 | 提供可信备考资料 |
| 任务 | 类型、阶段、进度、错误、重试与中断状态 | 后台执行与恢复 |
| 日报 | 日期、截止时间、事件次序、摘要版本、更正记录 | 稳定回看 |

列表接口采用数据库分页，区分总数与当前页，避免把全部历史新闻读进内存后分页。日期序和相关性序应明确可选，不能先按搜索相关性截取 500 条，再静默按日期重排当作完整结果。
